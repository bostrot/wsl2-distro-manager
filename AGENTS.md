# WSL2 Distro Manager — Agent Instructions

## What This Is
Flutter desktop app (Windows x64 only) for managing WSL distributions. Uses Provider for state management and `fluent_ui` for Windows-native UI.

## Commands

| Task | Command | Notes |
|------|---------|-------|
| Get deps | `flutter pub get` | 2-3 min, do not cancel |
| Static analysis | `flutter analyze` | Must pass before PR |
| Run tests | `flutter test` | Needs WSL installed; 2-5 min |
| Run e2e tests | `flutter test integration_test/` | UI click-through tests; ~4 min |
| Run dev | `flutter run -d windows` | Hot reload enabled |
| Build release | `flutter build windows` | 3-8 min; output in `build/windows/x64/runner/Release/` |
| MSIX package | `dart run msix:create` | Config in `pubspec.yaml` under `msix_config` |
| Check translations | `dart run scripts/check_translations.dart` | Run before every build; CI gate |

**Required setup:** `flutter config --enable-windows-desktop`

## Testing
- Tests in `test/` cover WSL, Docker images, templates, paths, etc.
- WSL-dependent tests create/delete real distro instances; require WSL available
- `test/mocks.dart` has shared mock utilities (MockShell, MockHttpClientAdapter, etc.)
- Integration tests in `integration_test/` simulate clicking through the app UI (navigation, dialogs, license screen, AI panel, AI Workspace, settings)
- Use `ValueKey('test-*')` keys on widgets that need to be found by e2e tests
- **`ValueKey`s must be unique per list item**, not hardcoded per widget-shape. A shared literal key across N repeated widgets (e.g. one `Button` per card in a list) causes `find.byKey()` to throw "ambiguously found multiple widgets" once all N are simultaneously mounted — this can stay hidden for a long time if the widgets are gated behind a loading state during earlier testing, then surface the moment that loading is fixed/sped up. Prefer `ValueKey('test-foo-${item.id}')`.
- **Integration test setup:** Always initialize `prefs = await SharedPreferences.getInstance()` in `setUp()` before pumping the widget
- **`MockShell.run()` (`test/mocks.dart`) matches on `arguments.contains(...)` and positional indices** (`arguments[1]`, `arguments[2]`, …), and ignores the `executable` parameter entirely. This breaks for SSH-wrapped remote calls, since `ssh` prepends ~10 option tokens before the real subcommand, shifting every position. New remote-path tests should assert via `.contains(...)` only — never rely on positional indexing — or extend the mock to be SSH-shape-aware (locate `--` and index relative to it).
- **`Notify.message`** (`lib/components/notify.dart`) is a `static late Function` with no default value or initializer. Any code path under test that calls it — including service/API-layer code, which is an accepted pattern here (see `lib/api/templates.dart`, `lib/components/sync.dart`, `lib/api/ai_workspace/service.dart`) — throws `LateInitializationError` unless the test stubs it first: `Notify(); Notify.message = (msg, {duration, loading = false, useWidget = false, leadingIcon = true, dynamic widget}) {};` in `setUpAll()`.
- **Integration tests run via `LiveTestWidgetsFlutterBinding`** (`flutter test integration_test/foo.dart -d windows` — a real windowed app, not a synthetic canvas). `tester.view.physicalSize`/`devicePixelRatio` overrides do **not** affect layout here the way they do in standard widget tests — the real window's current size/DPI scaling governs layout, and can't be forced from the test. Don't write assertions that depend on display-mode breakpoints (e.g. fluent_ui's compact/open threshold) being controllable this way.
- **Long/looping `flutter test ... -d windows` runs can have their output silently truncated** by tool-output capture on multi-failure runs. When debugging, redirect to a file (`... > out.txt 2>&1`) and read the file directly rather than trusting truncated tail output.

## fluent_ui Gotchas
- **Icons:** `FluentIcons.sparkle` does not exist — use `FluentIcons.flag` or `FluentIcons.star` instead
- **`_solid`/`_fill` icon variants are risky:** e.g. `crown_solid`, `lightbulb_solid` are declared in the Dart bindings but may not exist in the bundled `FluentIcons.ttf` subset, rendering as a blank/tofu glyph. Before using a `_solid`/`_fill` variant, grep the codebase for existing usage as proof it renders — as of this writing there is none in production code (the only prior example, `heart_fill` in `lib/components/navbar.dart`, is dead/unimported code). Prefer the base variant (`crown`, `lightbulb`, …) unless you can visually confirm the solid one renders.
- **`PaneItem.title` must be a literal `Text` widget**, never a `Row`/composite. fluent_ui extracts the label via a `Text`-only property getter (`getProperty<String>()`); a non-`Text` title silently renders as an empty box — icon only, in *every* display mode, no error. Put badges/pills (e.g. a "NEW" tag) in `PaneItem.infoBadge`, not inside the title widget.
- **`PaneDisplayMode.auto` only shows labels (open mode) at window width ≥ 1008 logical px** — below that it's compact (icon-only + tooltip-on-hover). The app's default launch size must clear this or the nav pane looks perpetually broken. (`main.dart` sets `windowManager.setSize(...)` — keep it ≥ ~1180 wide.)
- **In compact mode, the nav item title is carried by `Tooltip.richMessage`, not a `Text` widget** — `find.textContaining()` won't find it there. For display-mode-independent integration tests, prefer asserting on the icon (`find.byIcon`) over the title text.
- **IconButton:** Does not support `tooltip` parameter — wrap in `Tooltip()` widget manually
- **ButtonSize:** `ButtonSize.small` is invalid — use default sizing only
- **ProgressRing:** No `width`/`height` params — wrap in `SizedBox.square(dimension: N)` instead
- **ToggleSwitch:** Exists in app bar but may be obscured by `WindowCaption` drag layer in tests — use `warnIfMissed: false` when tapping
- **NavigationAppBar / NavigationPane:** May not be directly findable via `find.byType()` in integration tests due to widget tree structure — prefer `find.byType(NavigationView)` or text-based finders instead
- **FilledButton:** Imported from both `fluent_ui` and `material` — avoid importing `flutter/material.dart`; use `flutter/foundation.dart` if needed

## WSL / Windows Subprocess Gotchas
- **`wsl.exe` output is UTF-16LE** — must be decoded as raw bytes with null-byte stripping (see `ExecutionBroker.decodeWslOutput`). Don't assume `stdoutEncoding: systemEncoding` works for `wsl` invocations.
- **`wsl.exe` error text is localized** (e.g. German on a German-locale Windows install) — never match stderr on English substrings like `"not found"`. Match on the stable WSL error *code* instead, e.g. `WSL_E_DISTRO_NOT_FOUND` — the `Wsl/Service/WSL_E_*` code suffix is not translated, even when the surrounding sentence is.
- **`wsl --install -d <name>` does not create a distro under a custom name** — `-d` there just targets an existing distro for other purposes; it's easy to misread as "install as \<name\>". To register a *new*, distinctly-named distro, use the positional + option form: `wsl --install <Distribution> --name <Name>`.
- **When launching an SSH command through a non-`ssh` executable** (Windows `start`, `wt`, `powershell -command`, anything where `ssh` isn't the process itself), the literal `'ssh'` token must be manually prepended to the argument list. Helpers like `_buildRemoteArgs()` in `wsl.dart` return only ssh's *options* (`-o ...`, target, subcommand) — they don't include the `ssh` executable name, because `_runWsl`/`_startWsl` pass `'ssh'` as the process executable directly. Any code that instead launches via `start`/`wt`/etc. must prepend `'ssh'` itself or the command silently launches garbage.
- **`ExecutionRequest.timeout` is enforced via `.timeout()`** in `ExecutionBroker.run()`, but on timeout the underlying OS process is *not* killed (`Shell.run` wraps `Process.run`, which exposes no killable handle) — the Future gives up waiting, but a hung `wsl.exe`/`ssh` can still linger as an orphan. Repeated hangs during manual testing can leave many orphaned `wsl.exe`/`wslhost.exe` processes that contend with each other and cause *cascading* unrelated failures (check `Get-Process wsl,wslhost` if WSL starts behaving erratically after heavy manual testing, and kill stragglers).
- **A distro can fail to start (`Wsl/Service/CreateInstance/E_FAIL`) purely from low host disk space** — always check `df -h /c/` (or equivalent) when a WSL start failure doesn't otherwise make sense.
- **WSL2's per-distro VHDX never auto-shrinks.** Deleting data inside a distro (e.g. `docker system prune`) frees space inside the distro's filesystem but does *not* reclaim host disk space — the dynamically-expanding `.vhdx` file stays at its high-water mark. Reclaiming it needs `wsl --terminate <distro>` then `Optimize-VHD -Path <path> -Mode Full` from an **elevated** PowerShell (Hyper-V module) — cannot be done from a non-admin context.
- Per-distro VHDX location/GUID mapping: `HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss` maps each distro's GUID subkey to its `DistributionName` and `BasePath` (under `%LOCALAPPDATA%\wsl\`).

## State Management Patterns
- `GlobalVariable` class in `helpers.dart` holds static state flags (e.g., `aiPanelVisible`, `testProEnabled` for forcing Pro in tests/dev without a real license)
- `prefs` is a global `SharedPreferences` instance — must be initialized before app build
- `LicenseManager()` is a singleton (`factory LicenseManager() => _instance`) — **never** wrap it in `ChangeNotifierProvider(create: (_) => LicenseManager())`. `Provider` calls `dispose()` on whatever `create` returns when the widget unmounts; since the "created" value is actually the shared singleton, this permanently breaks Pro-gating (AI chat, AI Workspace, anything checking `.isPro`) for the rest of the app session the first time the user leaves the License screen. Always use `ChangeNotifierProvider.value(value: LicenseManager())` instead — `.value()` does not take ownership of the instance's lifecycle.
- **Business model is one-time Store purchase, not subscription.** There was a Stripe-subscription experiment (test-mode only, never live); it has been fully removed — no license keys, no validation backend, no quota, no billing portal. If you find docs/comments referencing "monthly/yearly plans" or `n8n.aachen.dev` license endpoints, they're stale. `LicenseManager().isPro` = `hasLegacyPro || isStoreLicensed`. Store detection works via **MSIX package identity** (`GetCurrentPackageFullName` via package:win32 in `_detectStoreInstall()`): a Store install runs packaged, the portable GitHub build doesn't. Consequences worth knowing: (1) `flutter run`/`flutter test` and the Debug exe are unpackaged → never Pro locally; use `GlobalVariable.testProEnabled`, `claimLegacyPro`, or the `LicenseManager.storeInstallCheckOverride` test seam (a **static** on the singleton — always reset to null in tearDown). (2) A self-built/side-loaded MSIX also gets Pro — accepted, the repo is open source so gating is an honor-system nudge, not protection. (3) The release pipeline DOES attach an `-unsigned.msix` to GitHub releases — deliberately left that way: it's load-bearing (`publish-store.yml` downloads exactly that release asset to submit to Partner Center), and an unsigned MSIX can't be installed without self-signing anyway, so it doesn't meaningfully undermine the gate; the portable `.zip` and the Inno `-setup.exe` both run unpackaged → free tier, as intended. `init()` also deletes the old Stripe-era prefs keys (`LicenseKey`, `LicenseStatus`, …) as one-time cleanup.
- `AiService` is a singleton for AI chat, powered **entirely by the user's own OpenAI-compatible key (BYOK)** — there is no app-operated AI backend and no query quota. `sendMessage()` throws `'pro-required'` without Pro and `'byok-required'` without a stored key; `hasByokConfigured` is a pure "is the key present" check (deliberately NOT Pro-coupled, so Settings can manage the key regardless of entitlement — the Pro gate lives in `sendMessage`/the UI, not in configuration state). There is no enable/disable toggle for BYOK anymore: with no backend, the key isn't an alternative route, it's the only one.
- `LicenseManager` also grants a permanent, honor-system "legacy Pro" to early purchasers via `claimLegacyPro(email)` (client-side only, not backend-verified — no way to cross-check Microsoft Store purchase records here — intentionally time-boxed via `legacyClaimWindowCloses`). `hasLegacyPro` reads straight from `prefs` on every access (not cached); when both legacy and store entitlements exist, `plan` reports `legacy`.
- App-wide long-running-operation feedback: `Notify.message(msg, {loading: true})` shows a bottom status bar with a spinner, callable from anywhere including service/API-layer code (not just widgets) — see `lib/api/ai_workspace/service.dart` for a multi-step example (distro setup → docker install → image pull, each with its own message)

## Architecture Notes & Known Gaps
- **AI Workspace** (Hermes Agent, OpenClaw, Open WebUI) runs in a dedicated `ai-workspace` WSL distro, created via `wsl --install Ubuntu --name ai-workspace` and always driven as root (`-u root`) — it's automation-only, no interactive login, so there's no default-user setup to skip. It's Pro-gated (`lib/screens/ai_workspace_screen.dart`); non-Pro users get a paywall and the screen never touches WSL. Docker isn't preinstalled on the bare Ubuntu image — `AiWorkspaceService._ensureDockerReady()` installs `docker.io` via apt on first Docker-backed tool use. The service's `init()` is split into `seedToolStates()` (sync) + `ensureDistro()` + independent per-tool `refreshStatus()` calls specifically so a UI layer can render immediately and update each tool's card as its own check resolves, rather than blocking behind one page-wide spinner.
- **`AiWorkspaceService` is a single shared instance provided from `main.dart`** (via `Provider<AiWorkspaceService>`, constructed once alongside `ExecutionBroker`), not a fresh instance per screen mount like it used to be — the AI Workspace screen now does `context.read<AiWorkspaceService>()` instead of constructing its own. This exists so `main()` can kick off `ensureInitialized()` (memoized: `seedToolStates()` + `ensureDistro()` + `refreshStatus()` for every tool, gated on `LicenseManager().isPro` at startup, not awaited) in the background *before* the user ever opens the screen — the whole point being that opening AI Workspace shouldn't cost 2-3 fresh `wsl` round trips every single time. `ToolState.checked` (false until a tool's first `refreshStatus()` completes, set in a `finally` so it's true even on error paths) is what lets the screen tell "genuinely not checked yet" apart from "checked and confirmed not installed" — both start out as `ToolStatus.notInstalled`, so status alone can't distinguish them. The screen's `initState()` only shows a checking spinner for tools where `checked != true`; a tool the startup background check (or an earlier visit to the screen, since the shared instance persists across navigation) already resolved renders immediately, no WSL call. `_retryInit()` still forces a full recheck of everything regardless, by explicitly repopulating the checking set. If you construct `WSLManager()` directly without going through `main()` (tests do this), it falls back to building its own `AiWorkspaceService` — the same optional-param-with-fallback pattern `executionBroker` already uses.
- **Remote WSL control** (SSH into a *remote Windows* host, then run `wsl.exe`/PowerShell there — not SSH into a Linux distro) is implemented directly in `WSLApi`/`MountService` via hand-rolled `shell.run('ssh', ...)` calls, gated by `_useRemoteWsl` (reads `UseRemoteWSL`/`RemoteWSLTarget` prefs, validated via the shared `lib/api/remote_target.dart` — don't re-duplicate that regex, it used to be copy-pasted 3x and could drift). Settings UI: `lib/screens/settings_screen.dart`.
- **`RemoteShell`/`ExecutionBroker` are not actually wired up for remote WSL** despite `doc/remote-execution-architecture.md` describing that migration as "✅ Complete" — verify claims in that doc before trusting them. Every production `WSLApi()`/`MountService()` call site uses the default constructor (no `broker` passed), so the `_broker != null` branches throughout `wsl.dart`/`mount_service.dart` are dead code today; remote execution actually happens through the plain `shell.run('ssh', ...)` fallback paths.
- **No macOS platform support exists** — no `macos/` directory, no Virtualization.framework/Swift code, nothing in `pubspec.yaml`. Verify before assuming any prior "started" work in this area; as of this writing it would be a from-scratch, multi-week undertaking (platform scaffolding + a parallel native VM-management abstraction), not a continuation.
- **AI Workspace tool install URLs are real, verified third-party projects, not fixed forever**: Hermes Agent installs from `https://hermes-agent.nousresearch.com/install.sh` (real binary: `hermes`, real project: NousResearch/hermes-agent) and OpenClaw from `https://openclaw.ai/install.sh` (real binary: `openclaw`, real project: openclaw/openclaw). The *original* URLs here (`get.hermes-agent.dev`, `install.openclaw.ai`) were placeholders that never resolved — `curl -fsSL <url> | sh` silently exits 0 even when curl fails to resolve the host (empty stdin still makes the piped shell "succeed"), so every install of those dead URLs reported success while installing nothing, and the next status check correctly found nothing there and reverted to "not installed". `AiWorkspaceService.install()` now prefixes every install command with `set -o pipefail;` so a dead curl target can't masquerade as success again — preserve that prefix (or the equivalent) if you touch install commands. Neither tool exposes a simple fixed HTTP port like Open WebUI does; both run as a background "gateway"/"daemon" process managed by their own CLI (`hermes gateway start/restart`, `openclaw gateway install --force && gateway restart`), verified from reading the real install scripts, **not fully live-verified end-to-end** — a live Hermes install (Python + Node + ffmpeg + an 8k-file git clone) is heavy enough that it briefly crashed WSL on a disk-constrained dev machine (`C:` at ~3.7GB free); recovered cleanly via `wsl --shutdown`, no data loss, but be aware these installs are not lightweight and don't repeat them carelessly on a low-disk machine. `_existsCheck()`'s `cmd://<binary>` scheme (`command -v <binary>`) replaced a per-tool `~/.foo` directory check for these two — that directory-tilde check is still used for any future tool that isn't docker- or PATH-based, but note `~` does **not** expand inside double quotes in bash (`[ -d "~/.foo" ]` silently always reports "missing" even when genuinely installed) — this is why the tilde-based check was wrong for hermes/openclaw in the first place.
- **"Open Dashboard" (`AiWorkspaceService.getDashboardUrl()`)** opens each running tool's web UI. Open WebUI is a bare static port (`ToolConfig.port` + `getUrl()`, no WSL round trip needed) — but Hermes and OpenClaw each need their own dashboard *server* explicitly started (`hermes dashboard` → `http://127.0.0.1:9119`; `openclaw dashboard` → `http://127.0.0.1:18789`, which prints a single-use pairing link rather than a bare URL), documented at their respective `docs.openclaw.ai/web/dashboard` and `hermes-agent.nousresearch.com/docs/.../web-dashboard` pages — not the same port as the `gateway` process. `ToolConfig.dashboardCommand` (null for Open WebUI) drives this: when set, `getDashboardUrl()` truncates a per-tool log file, spawns the dashboard command detached (`setsid ... & disown`, same technique as the gateway start commands), and polls the log for up to 5s for a `https?://` URL rather than assuming a fixed port — re-running the command is the documented, idiomatic way both tools expect you to "open or reopen" the dashboard, so it's safe to invoke on every click rather than trying to detect an already-running instance first. **Before returning that URL, `getDashboardUrl()` also polls it with a real HTTP request (`_waitUntilReachable`, injectable via the constructor's `reachabilityChecker` param for tests — never let this hit a real network stack in a unit test) for up to 10s.** This exists because `docker ps` reporting a container "Up" (or a gateway CLI printing its link) does not mean the web server inside has actually finished starting — without this, "Open Dashboard" would open a browser tab to a URL nothing was listening on yet, which renders as an empty response, not an error. Root-caused live on the dev machine: Open WebUI's container was found `Exited (255)` shortly after start, correlating with `C:` being critically low on free space (~3GB) — the same disk-pressure issue already diagnosed earlier for this container's startup (DB migration is write-heavy). That crash itself is an environment problem outside this fix's scope; what changed here is that the app now surfaces "couldn't open the dashboard" instead of a silent blank tab when it happens.
- **`AiWorkspaceService` persists each tool's last *confirmed* status/install path to `SharedPreferences`** (`AiWorkspaceStatus_<tool>` / `AiWorkspaceInstallPath_<tool>`, written by `_persistConfirmedState()`), so `seedToolStates()` can show a real answer on next app launch instead of a blank slate while `ensureInitialized()`'s background check re-verifies. `ToolState` has two independent booleans for this — don't conflate them: `hasKnownStatus` (true once there's *anything* real to show, cache or live — this is what the screen uses to decide spinner-vs-badge) and `checked` (true only once a *live* WSL check has completed this session — this is what gates whether a background refresh is still owed for that tool). A cache write only ever happens from a genuinely confirmed result — a successful command response, or an explicit "distro not found" WSL error code — never from a generic command failure or a caught exception, so a transient hiccup can't clobber good cached data with a wrong guess (`ExecutionBroker.run()` itself never actually throws — it always converts a shell-level failure into a failed `ExecutionResult`, so in practice both of those "don't persist" paths in `refreshStatus()` are reached via a non-zero exit code, not a raw Dart exception, despite what the `catch` block's placement might suggest). `_retryInit()` in the screen explicitly resets `checked` to false on every tool before re-running — otherwise a tool already verified earlier in the session would get silently skipped by the checked-gated background-refresh loop even on an explicit user retry.
- **`WslMcpService`** (`lib/api/mcp/wsl_mcp_service.dart`) runs a Pro-gated local MCP (Model Context Protocol) server exposing the WSL API to external MCP clients (Claude Desktop, other agent tools) — think "openterminal, but for WSL distros". Two tool families: one-shot (`wsl_list_distros`, `wsl_run_command`, `wsl_stop_distro`) and persistent terminal sessions (`wsl_terminal_start/send/read/list/close`, backed by `WslTerminalManager` — see below). Deliberately excludes destructive/one-way operations (create, remove, export, move) from the MCP tool surface — those stay GUI-only where a human directly confirms them. Binds to **127.0.0.1 only** (never `0.0.0.0` — unlike the distro-sync server in `components/sync.dart`, which is intentionally LAN-reachable; this endpoint can run arbitrary commands and must never be network-reachable by default — see the Cloudflare Tunnel bullet below for the opt-in exception) on port 59133, and requires a locally-generated bearer token (shown once in Settings, `WslMcpService().token`) on every request. The underlying `HttpServer` reference is a **static** field (mirrors `Sync`'s `static late HttpServer server`) so every `WslMcpService()` instance shares the one real running server — tests that call `start()` **must** `tearDown` with `await WslMcpService().stop()`, or a "running" server from one test silently makes the next test's `start()` short-circuit via its own idempotency guard and never invoke that test's injected factory (`capturedHandler` stays null). The protocol core (`lib/api/mcp/mcp_server.dart`) implements only the synchronous request/response subset of MCP over JSON-RPC (`initialize`, `tools/list`, `tools/call`) — no SSE streaming, no resumable sessions — sufficient for "call a tool, get one reply" clients but not the full Streamable HTTP spec. When decoding `params`/`arguments` from a message map, don't use a rigid `as Map<String, dynamic>` cast — maps not produced by `json.decode` (e.g. Dart literals in tests) can have different generic parameters and throw; normalize via `Map<String, dynamic>.from(...)` instead (checked via `is Map` first).
- **`WslTerminalManager`** (`lib/api/mcp/wsl_terminal_manager.dart`) gives MCP clients persistent, session-based shell control (start a session, send input over time, poll for output, close it) as opposed to `wsl_run_command`'s one-shot exec. Built on `WSLApi.startShell()`, which spawns `wsl -d <distro> -u <user>` with **no trailing command** — the exact same "drop into the distro's default shell, read commands from stdin" primitive `execCmds()`/`runCmds()` already use elsewhere in `wsl.dart`, not a new way of talking to WSL. `WslTerminalManager`'s session map is owned by `WslMcpService` and is **static** for the same sharing reason as `_server`; `WslMcpService.stop()` calls `closeAll()` so disabling the MCP server can't leave orphaned WSL shell processes running. **Testing gotcha**: `test/mocks.dart`'s shared `MockProcess.exitCode` resolves to `0` immediately, which is fine for one-shot commands but wrong for anything simulating a long-lived session (`WslTerminalSession`'s constructor does `process.exitCode.then((_) => _closed = true)`, so a session backed by `MockProcess` looks "already closed" almost immediately) — use a dedicated fake process with a `Completer`-backed `exitCode` that only resolves when the test wants it to (see `test/wsl_terminal_manager_test.dart`'s `_FakeProcess`) instead.
- **`CloudflareTunnelService`** (`lib/api/mcp/cloudflare_tunnel_service.dart`) is the opt-in exception to "MCP server never leaves 127.0.0.1": it runs a `cloudflared` quick tunnel (`cloudflared tunnel --url http://127.0.0.1:59133`, no Cloudflare account needed) to get a temporary public HTTPS URL, gated behind the MCP server itself being enabled first. Once this is on, the bearer token is the *only* thing protecting the endpoint from the entire internet — the Settings UI shows a persistent warning `InfoBar` for this reason, and `WslMcpService.stop()` also tears the tunnel down (a public URL routing to a dead server is worse than no URL). `cloudflared` is located via (in order) a previously-downloaded copy cached under `getDataPath()/bin/cloudflared.exe`, then PATH, then downloaded fresh from Cloudflare's official GitHub releases — same static-field sharing pattern as `WslMcpService`/`Sync`. **Never live-test the download/spawn path carelessly**: a real `cloudflared` invocation pulls a ~30-40MB binary and spawns a real outbound connection — for tests, always inject `binaryLocatorOverride` and `processSpawner` (see `test/cloudflare_tunnel_service_test.dart`) rather than exercising the real thing, and the integration test for the Settings toggle (`integration_test/mcp_settings_test.dart`) deliberately verifies the UI renders without ever tapping the toggle itself.
